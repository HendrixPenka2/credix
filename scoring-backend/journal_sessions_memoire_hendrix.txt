Plusieurs points mal compris depuis les sessions précédentes ont été

0.1 Confusion XGBoost / LightGBM dans le prompt maître
  → Le prompt maître apporté en session 6 mentionnait "XGBoost" (item 1
    des principes non négociables). ERREUR : le modèle est LightGBM.
  → Correction à apporter dans le template du prompt maître.
 
0.2 Origine des mots "aggravant" / "atténuant"
  → Source : une seule ligne Python dans shap_service.py :
    direction = "aggravant" if shap_value > 0 else "attenuant"
  → Pas d'IA, pas de base de données. Règle codée en dur.
  → Le signe SHAP (positif = aggravant, négatif = atténuant) est la
    convention choisie et documentée dans le projet.
 
0.3 Rôle de Gemini Flash dans le système
  → Gemini était utilisé UNE SEULE FOIS dans generate_metadata.py pour
    générer les libelle_agent et les gabarits de phrases par feature.
  → Les gabarits_aggravant / gabarits_attenuant ont été abandonnés en v2
    (incohérences contra-intuitives sous interactions non-linéaires).
  → Seul libelle_agent reste exploité à l'inférence.
  → Gemini peut être remplacé par une saisie manuelle : aucun impact sur
    le pipeline de scoring.
 
0.4 Distinction HomeCreditAdapter vs seed_database.py
  → HomeCreditAdapter = la "recette" : sait calculer les 27 features
    depuis des CSV. Ne touche pas MongoDB.
  → seed_database.py = le "cuisinier" : appelle l'adapter, écrit dans
    MongoDB. Tourne une seule fois.
 
0.5 Structure feature_metadata (27 documents MongoDB)
  Champs actifs à l'inférence :
    feature, run_id, libelle_agent, type, iv, is_declarative,
    is_request_specific, champs_source, seuils, modalites,
    document_recommande
  Champs morts (écrits par Gemini, jamais lus) :
    gabarit_aggravant, gabarit_attenuant
  Champs passifs (stockés pour analyses futures) :
    p25, p50, p75, p95, nan_rate, famille, formule, direction
 
0.6 Rôle des seuils vs p25/p75
  → p25/p75 ont servi UNE FOIS à construire les seuils dans generate_metadata.
  → Les seuils (intervalles avec labels) sont utilisés à chaque scoring
    pour produire le label lisible dans les phrases SHAP.
  → Les percentiles bruts sont devenus redondants après cette étape.
 
0.7 ETL de mise à jour des features catégorie C
  → Conçu (catégorie C protégée par le PATCH endpoint, message explicite).
  → Non implémenté car dataset Home Credit est statique.
  → À mentionner en perspectives mémoire : "pipeline ETL périodique

  → Le projet n'est pas minimaliste. Il est correctement scoped.

PARTIE 2 — CONCEPT PSI EXPLIQUÉ (à mémoriser pour soutenance)
================================================================

DÉFINITION :
  PSI (Population Stability Index) mesure si la DISTRIBUTION d'une variable
  a changé entre deux périodes. Il compare la forme de la courbe, pas la moyenne.

FORMULE :
  PSI = Σᵢ (Aᵢ − Eᵢ) × ln(Aᵢ / Eᵢ)
  Eᵢ = proportion dans la période de référence, bin i
  Aᵢ = proportion dans la période actuelle, bin i

INTERPRÉTATION :
  PSI < 0.10  → STABLE    — aucune action
  PSI < 0.25  → ATTENTION — surveiller
  PSI ≥ 0.25  → DÉRIVE    — réentraînement recommandé

DEUX IMPLÉMENTATIONS DANS CREDIX :

  calculer_psi() — utilisé par model-drift :
    Variables : scores PDO (300–850)
    Bins : 10 intervalles FIXES et ÉGAUX (55 points chacun)
    Pourquoi fixes : plage connue, signification métier par zone,
    comparaison stable dans le temps.
    Pourquoi 10 : convention industrie credit scoring (FICO, Moody's).
    Trop peu → on rate les shifts. Trop de bins → certains bins vides,
    log(0) diverge, PSI explose artificiellement.

  calculer_psi_generique() — utilisé par feature-drift :
    Variables : valeurs WOE de chaque feature NAP (plage inconnue, variable)
    Bins : QUANTILES de la distribution de RÉFÉRENCE (adaptatifs)
    Pourquoi quantiles : EXT_SOURCE_3 WOE peut aller de -2.5 à +3.0 selon
    les données. Impossible de fixer des bornes à l'avance.
    Retourne None si < 10 observations (pas 0.0 — None = "on ne sait pas").

DIFFERENCE model-drift vs feature-drift :
  model-drift  → PSI global sur les SCORES → dit SI le portefeuille a bougé
  feature-drift → PSI sur chaque WOE des 27 features → dit QUOI a bougé
  Le feature-drift est un SIGNAL PRÉCOCE : les variables dérivent avant le score.
  Exemple : EXT_SOURCE_3 PSI=0.35 DÉRIVE + score PSI=0.08 STABLE
  → le score masque la dérive d'une variable. feature-drift la révèle.

POURQUOI LES BINS PSI NE SONT PAS LES BINS WOE :
  Les bins WOE (OptimalBinning) convertissent valeur brute → valeur WOE (une fois,
  lors de l'entraînement).
  Les bins PSI découpent la DISTRIBUTION des valeurs WOE (l'output) pour comparer
  deux périodes. Ce sont deux niveaux d'abstraction distincts.
  En pratique, pour une feature avec 5 WOE distincts, les bins PSI correspondent
  naturellement aux 5 WOE levels (la variable est discrète).

RÉFÉRENCE PSI :
  = les données des 30 premiers jours après la promotion du modèle en PRODUCTION.
  C'est le "comportement normal attendu" de la population initiale.

4. **`form-schema` run_id** : lisait `admin_config["modele_actif"]`

### Clarification architecture AE/IF (discutée avec Hendrix avant de coder)
`_appliquer_ae()` réutilise en interne `encoder_if` et `if_metadata` (features_cat/features_total) — ce ne sont **pas** des artefacts IF-only mais un prétraitement partagé AE+IF. Seul `isolation_forest.pkl` (le modèle IF lui-même) est réellement mort une fois l'AE actif. Décision prise : garder les **11 fichiers obligatoires** à l'upload pour cette phase (Option A, zéro risque, backend déjà testé). Option B (rendre `isolation_forest.pkl` seul optionnel, patch backend `Optional[UploadFile]`) **gardée en attente pour la toute fin du projet**, à la demande explicite de Hendrix.
